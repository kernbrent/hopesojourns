# Hope Sojourns knowledge assistant implementation plan

Last reviewed: October 15, 2026

The internship assistant is a preview-only project. Brent authorized a tile on preview.hopesojourns.com and clarified that the main internship page and every video should support questions about any approved content, using page and video context to select evidence. A subsequent clarification extends contextual question buttons across photos, articles, devotionals, profiles, and journeys, with a warm uncertain-answer handoff into the existing journey-interest form. The assistant must identify itself as AI, never impersonate a live person, and only promise recorded follow-up after a successful intake. No test or production deployment, Git commit/push, paid service activation, external messages, or private-content publication is authorized by this work.

## Scope and phases

This is Major work. The initial single-interview production path was estimated at 40–80 engineering hours; extending ingestion and contextual answers across every site video is provisionally 60–120 hours, plus transcript review time. These are rough planning estimates, not promised delivery times. The existing preview remains the development destination until Brent authorizes otherwise.

1. **Implemented preview experience:** an internship landing page; public Athens interview selection; page/video/ministry context; typed source lookup; source links; unknown-answer fallback; feedback; proposal editing; evidence and privacy confirmation; separate reuse and FAQ publication; reject/follow-up; source correction/withdrawal; topic correction/merge; anonymous demo counts; all-time/30-day FAQ ordering; search relevance; essential pins; audit and analytics demonstrations. All changes live in one browser tab's session storage. Demo roles are not authentication. No actual AI, automatic transcription, microphone recording, spoken replies, web search, or MMT writes occur.
2. **Next secure text milestone:** approve isolated preview storage and a budget, implement the server data model and permission checks, connect one reviewed transcript plus approved website excerpts, then test the complete shared text workflow before expanding. This is deliberately incomplete today.
3. **Library ingestion:** inventory every public catalog, published story, embedded provider video, and authorized restricted video; deduplicate a full recording and numbered clips; record usage rights and content ownership; create full timestamped transcripts, not summaries. Persist processing jobs, correct names/timestamps, review, then publish approved public segments. Never substitute captions for a transcript. Private ingestion must use a separate namespace and retrieval path.
4. **Voice:** add explicit start/stop/cancel recording, duration limits, consent, text fallback on denial/failure, and optional spoken replies with AI voice disclosure. No microphone permissions or browser speech services are requested by the current demo.
5. **Broader coverage and controlled release:** approved ministry sites, selected documents, devotionals, daily notes, captions, internship descriptions, and journey information. Add partner/general source labels and restricted approved-domain search only after cost/privacy approval and text-path verification. Production remains a later decision.

## Context and evidence design

A reusable data-ask-source attribute demonstrates the same entry point on information and image captions. The preview unknown-answer link opens the existing interest form with no question/contact details in the URL and no automatic submission. Real integration should reuse the inquiry workflow and assigned tasks with an explicit visitor submission, carry limited source/context references, and return a durable success receipt. Do not promise automatic replies or imply staff already received the question.

Pass stable page, content type, image/caption, destination, ministry, journey, video, segment, and playback-time identifiers to the server. They are untrusted hints, never access grants. Explicit question content can override an irrelevant page/video; ambiguous follow-ups retain recent context. Query approved source projections across the accessible corpus, prioritize relevant video/ministry evidence, and fall back to broader approved Hope Sojourns material when useful. Do not let current context hide a clearly requested different destination.

The prototype uses a finite keyword/alias lookup and verbatim website excerpts. It is not semantic retrieval or language-model conversation. It can recognize bedding aliases and selected follow-ups; reviewers can correct groups. Questions explicitly about what a speaker said require a transcript and currently return uncertainty. No timestamp is invented. Full implementation should evaluate lexical + embedding retrieval, claim-level citations, and timestamp spans. Costs, housing, eligibility, availability, academic credit, safety, and other commitments require explicit current authority. Conflicting evidence must produce uncertainty and a follow-up option.

Retrieved content is quoted data, never developer instructions. A future model receives only authorized evidence and cannot call MMT tools or send messages. Validate each cited source ID/revision and timestamp against the server-selected evidence after generation. Check relevant statement support, not just whether a citation exists. An earlier generated answer is not evidence; curated answers must retain original approved sources. Changes, withdrawal, permission changes, and deletion revoke dependent approvals, invalidate caches, and make stale results unavailable before reindexing completes.

## Proposed server additions not applied

Keep the current stack initially: a separate preview Worker/D1/R2 environment, D1 full-text retrieval for the small first corpus, R2 original/derived transcript artifacts, and an idempotent background job queue. Evaluate embeddings only when lexical tests show a gap; avoid adding a vector database before evidence requires it. Hosted OpenAI File Search reduces retrieval implementation work but adds storage/tool charges and external deletion coordination. Local D1 retrieval gives more direct source-version/permission control.

Proposed tables: `knowledge_sources` (stable origin, hash, revision, ministry/destination, kind, owner, public/restricted visibility, approval, publication/update dates, withdrawal), `knowledge_segments` (source revision, text, start/end seconds), `knowledge_jobs` (idempotency key, status, retry), `knowledge_conversations`, `knowledge_questions`, `knowledge_feedback`, `knowledge_topics`, `knowledge_topic_memberships`, `knowledge_candidates`, `knowledge_candidate_evidence`, `knowledge_faqs`, `knowledge_faq_evidence`, `knowledge_audit`, and `knowledge_usage_reservations`. No migration has been added or run. Require unique operation keys, transactional revisions, and append-only actor/time/action audit events. Store reusable approval independently from public publication. Edits revoke approval; publication requires underlying evidence and privacy review. Merge/split topic membership transactionally, then recompute distinct visitors instead of summing counts.

Extend existing user configuration with explicit booleans for `knowledge.view_queue`, `knowledge.edit_answers`, `knowledge.approve_reuse`, `knowledge.publish_faq`, `knowledge.manage_sources`, and `knowledge.view_analytics`. Existing read-only accounts receive no new write rights. Map administrators deliberately; reject unknown flags. Enforce in `authenticate`/route handlers and database queries, not only buttons. Test HS/CSM membership boundaries, revoked sessions, CSRF, and object-level access. These rights are not yet added to actual MMT configuration.

Proposed endpoints: a public answer route accepting limited context/history, feedback, published FAQ search, and public source excerpts; authenticated queue/proposal/review/publish/source/job/topic/analytics endpoints. Source URLs are constructed server-side from permitted records, not visitor-supplied arbitrary URLs. Use approved-host crawling, DNS/IP restrictions, redirect checks, HTML sanitization, and no credential forwarding to prevent SSRF and prompt injection. Keep all public caches and indexes independent of restricted material. Voice endpoints must apply the same authorization and source projection.

## Privacy and controls proposed for approval

For the current demo, sessionStorage stores raw questions/comments/answers only in that tab, with Clear my demo and no network submission. It does not provide shared records, actual distinct-visitor measurement, or reliable human identity. Browser restoration may retain a session; private device data must not be entered. Demo event limits are 20 questions/minute and 50/tab, and do not claim to be server abuse prevention.

For the server milestone, propose 30-day private conversation retention, explicit deletion controls, no raw audio retention after transcription unless separately approved, and anonymized topic aggregates. Use a random first-party visitor token with an explained retention window, no fingerprinting, and no raw IP analytics. Estimate browsers rather than people; cookie clearing, shared devices, and multiple devices introduce error. Count at most one visitor/topic/window while tracking total questions separately. Offer all-time retained aggregates, rolling 30 days, and 7-day trends. Default ranking: essential pins, then distinct visitors, then questions, then deterministic title; search relevance precedes popularity and pinning.

Propose limits of 600 question characters, bounded recent conversation turns, 5 requests/minute, 30/day/visitor, and a global daily cap. Add server abuse protection with privacy-reviewed challenge behavior, atomic concurrency reservations and maximum-token cost reservation before provider calls, fail closed if accounting fails, and a hard daily/monthly budget enforced in application code. Provider dashboard budgets alone are insufficient. Retain no unrestricted user identifiers or raw chats in public analytics or logs.

## Paid services remain disabled

API billing is separate from a ChatGPT subscription and does not provide access to ChatGPT conversations. Do not place permanent credentials in the browser or repository. A future Worker secret `OPENAI_API_KEY`, allowlisted `OPENAI_TEXT_MODEL`, `OPENAI_TRANSCRIPTION_MODEL`, `OPENAI_SPEECH_MODEL`, and `KNOWLEDGE_AI_ENABLED=false` would be required. Also configure isolated bindings, `KNOWLEDGE_DAILY_BUDGET_USD`, `KNOWLEDGE_MONTHLY_BUDGET_USD`, token/recording/job limits, approved partner hosts, and retention. Defaults must reject paid requests rather than silently selecting a provider/model.

Review a smaller text model against evidence tests before choosing it; compare with a stronger model only if accuracy requires it. Estimate text cost as requests × (input tokens × input rate + output tokens × output rate), including context and retrieved excerpts. As a planning example, 1,000 answers at 2,000 input and 400 output tokens cost $8 at assumed rates of $2/$10 per million tokens; this is an illustration, not a selected-model quote or approved budget.

Official pricing checked October 15 lists mini transcription at approximately $0.003/minute (120 minutes ≈ $0.36), and another transcription option at $0.006/minute (120 minutes ≈ $0.72). Verify required timestamp/diarization support and evaluated quality before selecting a model; transcript review labor is separate. Voice generation, live audio, web search, file retrieval, token usage, and storage have separate rates. File Search lists $0.10/GB/day after its free allowance and $2.50/1,000 tool calls; web search lists $10/1,000 calls plus content tokens. Existing Cloudflare plan, D1/R2/Queues quotas, storage and delivery costs remain unverified; no new resources were created. Do not promise zero hosting charges. Keep paid services off until total budget and data-processing approval are explicit.

OpenAI API data is not used for training by default, but this does not mean zero retention. Responses storage and abuse monitoring have separate retention rules. Propose `store:false`, minimal excerpts/history, and no hosted conversations unless necessary; verify endpoint-specific retention, organization settings, and exceptions before launch. Sources: [official pricing](https://developers.openai.com/api/docs/pricing), [official data controls](https://developers.openai.com/api/docs/guides/your-data), and [Responses text guide](https://developers.openai.com/api/docs/guides/text).
